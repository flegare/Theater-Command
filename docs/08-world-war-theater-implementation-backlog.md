# 08 - World War Theater Implementation Backlog

**Status:** Prescriptive execution plan, revision 1, 2026-08-10  
**Product authority:** [`07-world-war-theater-northstar.md`](07-world-war-theater-northstar.md)  
**Execution target:** lower-tier coding models working one task packet at a time

## 1. Execution Rules

This backlog is ordered. A task may start only when all listed dependencies and its phase gate are complete. The implementing model must not reinterpret the architecture, rename modules, combine tasks, or begin later integration because a nearby implementation looks convenient.

For every task, the implementing model must:

1. Read north-star document 07, this section, the task row, and only the directly relevant existing files.
2. Restate the task ID, allowed scope, dependencies, and acceptance checks in its work note.
3. Inspect the current files before editing. Preserve unrelated user changes.
4. Use existing domain/application/infrastructure boundaries. Domain modules cannot import Express, React, SQLite, Ollama, filesystem, wall-clock, or global randomness.
5. Validate all external input with the shared Zod contract. Do not use `any`, unchecked type assertions, or catch-and-ignore behavior.
6. Add or update tests in the same task. A task without its specified tests is incomplete.
7. Run `npm run check` and the narrow relevant test command. Run the full suite when a shared contract, migration, tick, perspective, or API boundary changes.
8. Report files changed, commands run, test result, and any follow-up risk. Do not claim completion when an acceptance condition is unverified.
9. Update only that task's status marker from `[ ]` to `[x]` after acceptance passes. Do not mark dependent tasks complete.

## 2. Non-Negotiable Constraints

- New campaign code lives under `theater_campaign`; do not grow `admiral_dashboard` into the campaign app.
- The normal application must run locally on Windows with Node.js, npm, SQLite, and optional Ollama. No Docker, Python, cloud account, Redis, PostgreSQL, or external tile service is required for core tests.
- Bind the server to `127.0.0.1` by default. A non-loopback bind requires explicit configuration.
- Ground truth, observations, and country belief state are separate data models.
- Normal API responses are projected for the campaign player's country before serialization.
- Normal APIs never return an enemy truth unit ID, exact hidden position, hidden route, stockpile, readiness, or secret order.
- God Mode is enabled server-side only with `GOD_MODE_ENABLED=1` and uses `/api/dev/*` routes.
- All simulation randomness uses the seeded random service. Domain code cannot call `Math.random()`, `Date.now()`, or `new Date()`.
- Ollama can propose. It cannot mutate state, call application commands, write files, or receive ground truth unavailable to its country.
- The campaign must remain playable and deterministic with Ollama offline.
- Sea Power integration tasks `SP-*` and `TEL-*` are blocked until Gates A-F pass.
- Never edit `Sea Power_Data\StreamingAssets\original`.

## 15. Recommended Assignment Order

Do not distribute every task in parallel. Use these lanes only where dependencies permit:

```text
Lane 1 - Platform:    FND -> DB -> API -> OPS
Lane 2 - Simulation:  SCN -> SIM -> GEO/FOR/MOV/ORD -> RES
Lane 3 - Knowledge:   INT -> REC -> SHR/DEC -> SEC/DEV
Lane 4 - Product UI:  UX follows completed API contracts only
Lane 5 - Content:     scenario/doctrine/catalog seeds follow schemas
Lane 6 - AI:          AI begins only after deterministic staff loop
Lane 7 - Integration: CAT/SP then TEL after their hard gates
```

At most one model owns a migration sequence or shared contract module at a time. Parallel tasks may not edit the same source files. The coordinating model runs full checks and resolves integration after each 3-5 task batch.
